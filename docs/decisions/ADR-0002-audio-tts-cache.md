# ADR-0002 · Audio via TTS with on-device caching

## Context

v0.1.0 ships without recorded audio (PRD §6: first version uses TTS, human
recordings come later). The offline constraint (`REQ-029`) requires audio to be
cached after first generation, and a listening task must not dead-end when
audio is unavailable (`REQ-017`, design-spec: audio failure is skippable).

## Decision

Audio is generated by a TTS provider on first request and cached on the
device; later plays read from the cache. The audio pipeline sits behind one
internal interface so the provider can be replaced (human recordings in a
later version) without touching call sites. When offline and uncached, the
audio area shows the fixed "needs network" state and the listening task offers
skip; the practice flow never blocks on audio.

## Consequences

- First plays of a phoneme require network; repeated plays work offline.
- Replacing TTS with recorded audio is a pipeline change, not a feature change.
- Cache eviction is unspecified for v0.1.0 (device-managed storage).

## Rejected alternatives

- **Pre-generated audio files shipped in the bundle** — kept as the documented
  fallback in the SRS contingencies; rejected as primary because it bloats the
  bundle and hardens the update path before the phoneme data has stabilised.
- **Human recordings in v0.1.0** — out of scope per PRD §6 release plan.
